# OCodeJS Observability and Alert Operations

Status: operational specification. The thresholds below are proposed starting points, not configured alerts or measured SLOs.

## Scope

Applies to the staging Control API, staging MCP Worker and Account Portal Preview. GitHub Pages is a static frontend and should be monitored separately from backend service health.

## Signal model

Every backend request should carry:
- `requestId`: generated by the server if absent; validate length and allowed characters when accepting a caller value.
- `service`, `environment`, `routeTemplate`, `method`, `statusCode`, `durationMs`.
- Optional `traceId` and provider request ID.
- Timestamp in UTC.

Do not record raw URL query strings, request/response bodies, cookies, authorization headers, API keys, OAuth codes, passwords or database URLs. Prefer route templates (for example `/api/v1/services/{serviceId}`) over concrete identifiers.

## Required metrics

| Metric | Type | Labels | Purpose |
|---|---|---|---|
| `http_requests_total` | Counter | service, environment, route, method, status_class | Request volume and error ratio |
| `http_request_duration_ms` | Histogram | service, environment, route, method | Latency percentiles |
| `dependency_check_total` | Counter | service, dependency, outcome | Dependency health |
| `mcp_handshake_total` | Counter | environment, outcome, protocol_version | MCP initialize reliability |
| `mcp_tool_list_duration_ms` | Histogram | environment | MCP discovery latency |
| `auth_events_total` | Counter | environment, provider, outcome | Authentication success/failure trends |
| `rate_limit_rejections_total` | Counter | service, route, client_tier | Abuse and quota pressure |
| `worker_cpu_time_ms` | Histogram | service, environment | Runtime resource pressure |

Never use user IDs, email addresses, API keys, session IDs, full URLs or arbitrary tool names as metric labels. Keep cardinality bounded.

## Proposed alert policy

These are initial thresholds to tune after collecting a staging baseline; they are not live alerts.

| Alert | Suggested condition | Severity | First response |
|---|---|---|---|
| API elevated 5xx | 5xx ratio > 5% for 5 min and at least 50 requests | High | Inspect release, dependency failures and correlated request IDs |
| API latency | p95 > 1,500 ms for 10 min | Medium | Break down by route and dependency |
| Readiness failure | Required dependency fails 3 consecutive probes | High | Confirm dependency state; avoid restart loops |
| MCP handshake failure | > 10% failures over 10 min and at least 20 attempts | Medium | Verify protocol version, endpoint and timeout |
| Auth failure spike | Failure rate > 3x 7-day same-hour baseline for 10 min | High | Check provider incidents and credential abuse; do not log secrets |
| Rate-limit surge | Rejections > 5x baseline for 5 min | Medium | Inspect aggregate source patterns; preserve privacy |
| Missing telemetry | No expected heartbeat for 10 min | High | Check Worker deployment and observability pipeline |

For low-traffic services, use synthetic checks and consecutive-failure rules rather than percentage-only alerts.

## Dashboards

1. **Service overview:** availability, readiness, request rate, 4xx/5xx ratio and p50/p95/p99 latency.
2. **Dependencies:** per-dependency outcome, latency and last successful check.
3. **MCP:** handshake success, tools/list duration, protocol version and sanitized errors.
4. **Identity:** sign-in outcome counts, callback errors and session revocation counts; no identity values.
5. **Security:** rate-limit events, authorization denials, privileged changes and suspicious spikes.
6. **Release health:** deploy version, commit SHA, CI run, error ratio before/after release.

## Retention and access

- Define retention by data class before enabling centralized storage.
- Restrict logs and traces to operational roles; audit access to sensitive telemetry.
- Keep high-cardinality diagnostic details in access-controlled logs, not metric labels.
- Apply deletion and retention rules consistently across backups and exports.
- Do not claim compliance or a specific SLO until policy, measurement and evidence exist.

## Staging verification checklist

- [ ] Confirm Worker logs and traces are enabled with query-string redaction.
- [ ] Confirm request IDs appear in response headers and structured logs.
- [ ] Confirm Authorization, Cookie and Set-Cookie values are redacted.
- [ ] Confirm no request bodies or secrets are recorded.
- [ ] Confirm metric labels have bounded cardinality.
- [ ] Run synthetic liveness/readiness checks and capture status/latency.
- [ ] Validate one controlled failure and confirm the alert path (without paging real users).
- [ ] Record the actual retention policy and access roles.

## Current known boundary

The current project documentation reports Worker Logs/Traces enabled for staging. Centralized metrics, queryable audit storage and alert rules remain pending. This document does not create dashboards, alerts, storage, telemetry resources or paid services.
